# Design b618: Write commands

Five subcommands, `propose`, `record`, `review`, `reaffirm` and `authorise`, operate the method: each plans one commit, shows it, and makes it. The work sits in an exported package, `github.com/nbyoung/tabloio/action`, that `tablotui` imports (D1); `cmd/tabloio` only parses arguments and prints. Four choices shape the design:

- **A plan is data.** Every command returns a `Plan`: the identity, the message, the trailers, the new bytes of each file, the planned tree and its diff. `--dry-run` prints the plan; `Apply` makes exactly that commit or none.
- **The facts come from tablo, the bytes from Git.** The package reads no task file. It takes a task's junctions, status, reviews and authorities from `tablo` through one interface, `Source`, and it edits a status file as lines of text.
- **A command refuses what the method cannot read.** A review by the wrong hand, a status at a gate that does not apply, `complete` before the last gate: each is a typed refusal that names the rule, before anything is written (D3).
- **Two proofs close every plan.** Git parses the composed message and must return exactly the planned trailers; tablo validates the planned tree and must report no error that the tree at `HEAD` does not already have.

## The model

### Packages

| Path                     | Holds                                                                                  |
|--------------------------|----------------------------------------------------------------------------------------|
| `action/`                | The exported package: requests, `Plan`, `Apply`, `Source`, refusals. Standard library only |
| `cmd/tabloio/write.go`   | The five subcommands: arguments to a request, the plan to stdout, the prompt, exit codes |

### The exported surface

```go
// Package action plans and makes the commits that operate the Tableaux
// method. A plan function changes neither a ref, the index nor the working
// tree; Apply makes the planned commit or leaves the checkout as it found it.
package action

// Repo is one checkout of a Tableaux project.
type Repo struct {
	Dir    string    // the project directory, as -C names it; "" is the working directory
	Source Source    // the project's facts; nil means Tablo{Dir: Dir, Env: Env}
	Env    []string  // added to the environment of every git and tablo child process
	Rand   io.Reader // the source of a fresh id; nil means crypto/rand.Reader
}

// Agent names what ran. The zero value adds no trailer.
type Agent struct {
	Model    string // the value of Model:
	CoAuthor string // the value of Co-Authored-By:, "Name <email>"; refused without Model
}

// Options are common to the five commands.
type Options struct {
	Agent   Agent
	Subject string // replaces the default subject; one line
	Body    string // paragraphs between the subject and the trailers; "" for none
}

// Proposal is a new task.
type Proposal struct {
	Title, Description string
	Parent             string      // required: propose never creates a root
	Assignee           string      // "" means the author's email
	Order              int         // 0 means one above the largest order among the parent's children
	References         []Reference // in the order given
	ID                 string      // "" draws a fresh id
}

// Reference is one entry of a task's references.
type Reference struct{ URL, Text string }

// Recording is a record request. An empty Gate, State, Reason or Note keeps
// the field as "Resolving a record" states.
type Recording struct {
	ID                        string
	Gate, State, Reason, Note string
	NoReason, NoNote          bool // remove the field
	Pin                       bool // also commit the moved pins of the task's recursive junctions
}

// Propose plans the commit that adds tasks/<id>.yaml.
func (r *Repo) Propose(ctx context.Context, p Proposal, o Options) (*Plan, error)

// Record plans the commit that writes status/<id>.yaml, moves a pin, or both.
func (r *Repo) Record(ctx context.Context, rec Recording, o Options) (*Plan, error)

// Review plans an empty commit with one "Reviewed: <id> <gate>" per task.
func (r *Repo) Review(ctx context.Context, ids []string, gate string, o Options) (*Plan, error)

// Reaffirm plans an empty commit with one "Reaffirmed: <id>" per task.
func (r *Repo) Reaffirm(ctx context.Context, ids []string, o Options) (*Plan, error)

// Authorise plans an empty commit with one "Authorised: <id>" per task.
func (r *Repo) Authorise(ctx context.Context, ids []string, o Options) (*Plan, error)

// Apply makes the planned commit. It returns a Refusal with the code stale
// when the checkout no longer stands where the plan read it.
func (r *Repo) Apply(ctx context.Context, p *Plan) (Result, error)

// Plan is a commit that does not exist yet: the dry-run form.
type Plan struct {
	Command           string       // "propose", "record", "review", "reaffirm" or "authorise"
	Tasks             []string     // the ids the commit concerns, in the order given
	NewID             string       // propose: the id allocated
	Branch            string       // the checked-out branch; "" on a detached HEAD
	Base              string       // the full hash of HEAD when planned
	Author, Committer Identity     // as Git will write them
	Subject, Body     string
	Trailers          []Trailer    // task trailers in the order given, then Model, then Co-Authored-By
	Files             []FileChange // sorted by path
	Pins              []PinChange  // sorted by path
	Tree              string       // the tree the commit will have
	Diff              string       // git's diff from the tree of Base to Tree; "" for an empty commit
	Warnings          []Warning
}

// Message returns the commit message: the subject; a blank line and the body
// when there is one; a blank line and the trailers, one per line, as one
// final paragraph. It ends with one newline.
func (p *Plan) Message() string

// String returns the shown form (design/b618/plan.txt).
func (p *Plan) String() string

type Identity struct{ Name, Email string }
type Trailer struct{ Key, Value string }
type FileChange struct {
	Path     string // relative to the repository root, with forward slashes
	Old, New []byte // Old is nil for a file the commit creates
}
type PinChange struct{ Path, Old, New string } // a submodule path and two full hashes
type Warning struct{ Code, Task, Text string }
type Result struct{ Commit string } // the full hash of the new commit

// Refusal is a rule that stops a plan. Code is stable; Rule is the RULES.md
// id the commit would break, when one exists.
type Refusal struct{ Code, Task, Gate, Rule, Text string }

func (e Refusal) Error() string

// Refusals is every refusal of one plan; a plan function returns it as its error.
type Refusals []Refusal

func (e Refusals) Error() string

// ExecError is a git or tablo run that failed for a reason outside the method.
type ExecError struct {
	Tool   string
	Args   []string
	Exit   int
	Stderr string
}

func (e *ExecError) Error() string
```

`Source` carries what the package asks of tablo. `Tablo` implements it in process, through tablo's library, as the owner ruled at review on 2026-10-06 (D2, A1 to A6, A8); the facts it asks for are those the executable's envelope carries, and the declarations below name them by the command that would print them. A test supplies a struct of fixed answers.

```go
// Source supplies the facts a plan needs and the two services tablo owns.
type Source interface {
	// Project returns the gate, state and reason keys in file order, and the
	// trunk's branch name, "" when undetermined.
	Project(ctx context.Context) (Project, error)
	// Task returns the derived facts of one task that exists.
	Task(ctx context.Context, id string) (Task, error)
	// Trailer returns one task trailer line without its newline; kind is
	// "authorised", "reviewed" or "reaffirmed", and gate is "" unless reviewed.
	Trailer(ctx context.Context, kind, id, gate string) (string, error)
	// Validate returns the validator's diagnostics for a tree.
	Validate(ctx context.Context, tree string) ([]Diagnostic, error)
}

type Project struct {
	Gates, States, Reasons []string
	Trunk                  string
}

type Task struct {
	ID, Title, Assignee string
	Children            []Child    // in display order; empty for a leaf
	Authorities         []string   // nearest first; the root lists its own assignee, the owner
	Junctions           []Junction // one per gate, in gate order
	Status              *Status    // the recorded status; nil when no file exists
	Reviews             []Review   // the effective reviews in the branch's history
}
type Child struct {
	ID    string
	Order int // 0 when the child states none
}
type Junction struct {
	Gate                         string
	Kind                         string // "plain", "recursive" or "not-applicable"
	Contributor, Model, Reviewer string // resolved; plain only
	URL                          string // recursive only
	Submodule                    bool   // recursive only: URL is a submodule path
}
type Status struct{ Gate, State, Reason, Note string } // "" for a field the file lacks
type Review struct{ Gate, By string }
type Diagnostic struct{ Severity, Code, Path, Message string }

// Tablo is the Source that calls tablo's library in process (decided at review).
type Tablo struct {
	Path string   // "" means "tablo" on the PATH
	Dir  string   // passed as -C
	Env  []string // added to the child's environment
}
```

### What every plan does

1. **Find the checkout.** `git rev-parse --show-toplevel --show-prefix` in `Dir`; the project is `<prefix>.tableaux`. No repository, no commit yet, or no `.tableaux` is an `ExecError`. `Base` is `git rev-parse HEAD`; `Branch` is `git symbolic-ref --short -q HEAD`.
2. **Read the identity.** `git var GIT_AUTHOR_IDENT` and `git var GIT_COMMITTER_IDENT`, run with the process environment plus `Env`, give the name and email that `git commit` writes: the environment's `GIT_AUTHOR_*` and `GIT_COMMITTER_*` before any configuration. The package never passes `-c user.*`, `--author` or an identity variable of its own; a caller sets one only by putting it in `Env`. Every check of whose hand acts reads these two emails, and a hand **holds** a position when the author's or the committer's email equals it, as README.md's Status and authorisation sections read a commit.
3. **Know the ids.** The ids are the names `<id>.yaml` that `git ls-tree --name-only HEAD` lists under `tasks/`. An id that is not four lowercase hexadecimal digits, or names no task there, is the refusal `no-task`, before any tablo run.
4. **Resolve the request** against `Source.Project` and `Source.Task` into trailers, file changes and pins, collecting every refusal; one refusal stops the plan (the sections below).
5. **Compose the message.** Each task trailer is the line `Source.Trailer` returns (A2); `Model: <model>` and `Co-Authored-By: <co-author>` follow when `Agent` states them. A body line that begins with `Authorised:`, `Reviewed:`, `Reaffirmed:`, `Model:` or `Co-Authored-By:`, in any case, is the refusal `body-trailer`: a blank line would part it from the block and Git would not read it. A subject that holds a line break or is empty is `bad-message`.
6. **Prove the trailers.** `git interpret-trailers --parse` reads `Message()` on stdin; its output must equal the planned trailers line for line, else the plan fails with an `ExecError` that quotes both. This follows SYNTAX.md, where a trailer sits in the final paragraph.
7. **Build the tree**, when the plan has a file or a pin. A file the plan changes must be clean (`git status --porcelain -- <path>` is empty) and a file it creates must not exist in the working tree, else `dirty`. With a private `GIT_INDEX_FILE` under a temporary directory: `git read-tree HEAD`; `git hash-object -w --stdin` for each new content; `git update-index --add --cacheinfo 100644,<blob>,<path>` for a file and `160000,<commit>,<path>` for a pin; `git write-tree`. `Diff` is `git diff --no-color --no-ext-diff --no-textconv --abbrev=7 --src-prefix=a/ --dst-prefix=b/ -U3 <base>^{tree} <tree>`. Planning therefore writes unreachable objects and nothing else.
8. **Prove the tree**, in the same case. `Source.Validate` runs on the tree of `Base` and on `Tree`. Every diagnostic of severity `error` in the second run that the first lacks, compared by code, path and message and leaving out `S11`, is the refusal `invalid` with the diagnostic as its text. S11 needs the history, which a bare tree lacks (A6); step 4 enforces it from `Task.Reviews`.

`Apply` then: checks that `HEAD` equals `Base`, that each changed file still holds `Old` (or does not exist) and each pinned submodule still stands at `New`, else `stale`; writes each `New` (mode 0644, creating directories) and runs `git add --intent-to-add` on a created file; runs `git commit --cleanup=verbatim --file=- --only -- <paths>`, with `--allow-empty` and no path for an empty commit, the message on stdin. `--only` leaves whatever else the user staged out of the commit and still staged. Hooks and signing run as the user configured them: no `--no-verify`, no `-S`. On a failed commit `Apply` writes each `Old` back, removes each created file after `git reset -q -- <path>`, and returns the `ExecError` with Git's own text; this settles prototype 518e's finding. After the commit it checks that `HEAD^{tree}` equals `Tree` and that the commit's message parses to the planned trailers; a difference means a hook rewrote the commit, and `Apply` returns the `Result` with the refusal `altered`. It never amends.

### The commands

`tabloio [-C DIR] [--tablo PATH] <command> [arguments]`. Every write command also takes:

| Option                   | Meaning                                                                                       |
|--------------------------|-----------------------------------------------------------------------------------------------|
| `--dry-run`, `-n`        | Print the plan and exit 0 without asking or committing                                        |
| `--yes`, `-y`            | Commit without asking                                                                         |
| `--message TEXT`, `-m`   | The subject in place of the default                                                           |
| `--body TEXT`            | A body; repeat it for several paragraphs                                                      |
| `--model ID`             | The `Model:` trailer; defaults to the environment's `TABLOIO_MODEL` (D5)                      |
| `--co-author 'N <E>'`    | The `Co-Authored-By:` trailer; defaults to `TABLOIO_CO_AUTHOR`                                |

`Plan.String()` is the shown form that [`b618/plan.txt`](b618/plan.txt) fixes: the line `<command> <ids> on <branch> at <base>`, with `a detached HEAD` for no branch and the base in seven digits; the `author` and `committer` lines; the message indented by four spaces between blank lines; `Diff`; then one line `warning: <code>: <text>` per warning. The command prints it to stdout. Without `--dry-run` or `--yes` it asks `Commit? [y/N] ` on stderr and reads one line from stdin: `y` or `yes`, in any case, commits; anything else prints `not committed` and exits 1. When stdin is not a terminal (`os.Stdin.Stat()` shows no character device) and neither option is given, it exits 2 and names both (D6). After the commit it prints `committed <short hash> <subject>`.

| Command | Arguments | Writes | Commit |
|---|---|---|---|
| `propose` | `--title T --description D --parent ID [--assignee E] [--order N] [--reference URL[=TEXT]]… [--id ID]` | `tasks/<id>.yaml`, new | The file; `Propose <title> (<id>)` |
| `record` | `<id> [--gate G] [--state S] [--reason R \| --no-reason] [--note T \| --no-note] [--pin]` | `status/<id>.yaml`, created or edited; with `--pin` the gitlink of each moved submodule | The file, the pins; `Reviewed:` where the hand reviews itself |
| `review` | `<id>… <gate>`: the last argument names the gate | Nothing | Empty; `Reviewed: <id> <gate>` per task |
| `reaffirm` | `<id>…` | Nothing | Empty; `Reaffirmed: <id>` per task |
| `authorise` | `<id>…` | Nothing | Empty; `Authorised: <id>` per task |

Options and positional arguments mix in any order; an option spelled with one hyphen and more than one letter is a usage error. A read option (`--ref`, `--markdown`, `--text`, `--level`, `--role`, `-o`) on a write command is a usage error: a write acts on the checkout's `HEAD` (A7).

**Default subjects.** `<title>` is the task's title with its first letter in lower case when its second is. `record` takes the first that fits: `Record <title> (<id>) at <gate>` when the gate changes; `Hand <title> (<id>) to review` when the reason becomes `review`; `Advance the pin of <path> for <title> (<id>)` for a pin alone; otherwise `Update the status of <title> (<id>)`. `review`: `Accept <title> (<id>) at <gate>`. `reaffirm`: `Reaffirm <title> (<id>)`. `authorise`: `Authorise <title> (<id>)`. With two to four tasks the three empty commits name `tasks <id>, <id>` in place of the title and id; with more, `<n> tasks`.

**What no command does.** Push, fetch, pull, merge, rebase, amend, tag, or switch branch. Stage or commit a path it did not plan. Set an identity or change a configuration. Move a submodule's checkout. Skip a hook. Edit or delete an existing task file. Write outside `.tableaux`, the gitlink of `--pin` apart.

### Propose

The file follows [`b618/task.yaml`](b618/task.yaml): `title`, `description` as a folded block wrapped at 78 columns from the description's words, `assignee`, `references` when any, each as one flow mapping, and `parent: { id: "<parent>", order: <n> }`, the id always in double quotes. The command writes no junction and no requirement: a new task inherits its junctions, and its author edits a departure by hand.

A fresh id is two bytes from `Rand` in hexadecimal, drawn again while a file of that name stands under `tasks/` or `status/` at `HEAD` or in the working tree; a thousand draws without a free id is an `ExecError`. Refusals: `no-task` for the parent; `bad-field` for an empty title or description, an assignee without `@`, a reference without a URL, a negative order or a line break in any field but the description; `id-taken` for a stated `--id` in use.

`propose` never writes `Authorised:`. The commit that adds the file is the task's deciding commit, so the task is authorised at once when the author is an authority and the commit lands on the trunk, and proposed otherwise; the trailer would restate that (D4).

### Resolving a record

With `t` the task, `old` its status (`undefined`, `undefined` when it has no file) and the gates in `Project` order:

1. `t` has no children, else `not-leaf` (S2).
2. `gate` is `--gate`, or `old.gate`. It names a gate, else `unknown-gate` (S5), whose junction for `t` is not `not-applicable`, else `gate-not-applicable` (S7).
3. `next` is the first later gate whose junction applies. The state follows the first case that fits:
   - `gate` is `undefined`: `--state` is absent or `undefined`, else `state-forbidden` (S4); the state is `undefined`.
   - no `next`: `--state` is absent or `complete`, else `last-gate-not-complete` (S8); the state is `complete`.
   - the junction at `next` is recursive: any of `--state`, `--reason`, `--note` is `recursive-holds-gate` (S9); the file holds the gate alone.
   - otherwise the state is `--state`, or `old.state` when the gate does not change; none is `state-required` (S10); `complete` is `complete-early` (S12), `undefined` is `state-forbidden` (S4), any other key outside `States` is `unknown-state` (S6).
4. The reason is `--reason`; none with `--no-reason`; else `old.reason` when the gate does not change, and none when it does, so a hand-off never outlives the gate it waits at (H5). A key outside `Reasons` is `unknown-reason` (S6). The reason `review` needs a reviewer at `next`, else `no-reviewer`.
5. The note follows the same rule. A note that is empty after trimming or holds a control character or a line break is `bad-field`.
6. **Reviews owed.** For each gate after `old.gate` up to `gate`, other than `defined`, whose junction is plain with a reviewer and has no entry in `t.Reviews`: when the hand holds the reviewer, the commit carries `Reviewed: <id> <that gate>`; otherwise the refusal `unreviewed` names the gate and the reviewer and suggests `--reason review` (S11). A junction's **reviewer** is its resolved `reviewer`, or the task's assignee when the junction states a `model` and no reviewer.
7. **Pins.** With `--pin`, the paths are the `URL`s of `t`'s recursive junctions that are submodules; none is `no-submodule`. A path enters `Pins` when `git -C <path> rev-parse HEAD` differs from the gitlink `git ls-tree HEAD` shows; none is `pin-unchanged`. Without `--pin` the command leaves every gitlink alone.
8. A plan with no field changed, no pin and no trailer of step 6 is `no-change`; `reaffirm` confirms a status that stands.

**The edit.** The command changes a status file line by line and never parses or dumps it. A field is unchanged when its resolved value equals `old`'s, and its lines keep every byte. Otherwise, in the order `gate`, `state`, `reason`, `note`:

- A field's lines are the first line that begins `<key>:` in column one and the indented lines after it, blank lines between them included, so a folded note goes whole.
- A changed field's lines become the one line `<key>: <scalar>`. A removed field's lines go. A new field enters after the lines of the nearest earlier field in that order, else before the nearest later one, else at the end.
- The line ending is the file's first one; a last line without one gains it before an insertion.
- A line in column one that is neither a comment, blank nor one of the four keys, or a key that appears twice, is `status-form`: the user edits such a file by hand.

**The scalar.** A value stays plain when it begins with an ASCII letter, is none of `true false yes no on off null y n` in any case, holds neither `: ` nor ` #`, and ends with neither `:` nor a space. Any other value goes in double quotes with `\` and `"` escaped. Inside a flow mapping (a reference of `propose`) a plain value also holds only `A-Za-z0-9 ._/~()'+=@%:#-`. So the note of 2026-10-05, `… shows live refresh: git-polling …`, is quoted, and so are `40e8`, `07e0`, `1000` and `2026-10-05`. [`b618/scalars.tsv`](b618/scalars.tsv) fixes thirty-four cases.

**Warnings**, which never stop a plan. The junction a record is **at** is the junction of `gate` when the gate changes and of `next` otherwise (D8). `not-contributor`: the hand holds neither that junction's contributor nor the assignee. `model-mismatch`: the junction states a `model` and `Agent.Model` does not begin with it (H3). `model-missing`: the junction states a `model`, the hand holds its contributor and `Agent.Model` is empty (H6).

### Review, reaffirm, authorise

Each takes one or more ids, refuses a repeated id as `bad-field`, and plans one empty commit or none.

| Command | Refuses | Why |
|---|---|---|
| `review` | `unknown-gate`; `gate-not-applicable`, for `undefined` too | H1: the method cannot read the trailer |
| | `not-leaf` | A parent's junctions are defaults; it has no work to accept |
| | `defined-review` | Authorisation stands as the review of `defined`; the text names `authorise` |
| | `recursive` | The subproject reviews its own work |
| | `no-reviewer` | The junction states none, so the trailer has no effect |
| | `wrong-hand`, naming the reviewer | H2: a review from another hand has no effect |
| `reaffirm` | `not-leaf`; `no-status`, a leaf with no file | Nothing recorded to confirm |
| | `recursive`, the next junction | The status date comes from the subproject |
| `authorise` | `off-trunk`: `Branch` is not `Project.Trunk`, or the trunk is undetermined | Authorisation reads the trunk's first-parent history alone |
| | `wrong-hand`, naming the authorities | The deciding commit counts only from an authority; the root's is the owner |

`review` reads no status: a reviewer accepts before or after the status passes the gate, and a second review is history. `reaffirm` warns `not-contributor` as `record` does. `authorise` accepts a task already authorised.

### Errors and exit codes

| Exit | When                                                                                                   |
|------|--------------------------------------------------------------------------------------------------------|
| 0    | The commit exists, or `--dry-run` printed a plan                                                       |
| 1    | A refusal, printed on stderr as `tabloio <command>: <task> <gate>: <text> (<code>, <rule>)`, one line each; or the user declined |
| 2    | A usage error, with the command's usage on stderr                                                      |
| 3    | An `ExecError`: no repository, no `tablo`, a failed hook, no identity; Git's or tablo's text on stderr |

The codes follow tablo's (A1). A plan is deterministic: the same checkout, environment, request and `Rand` give the same `Plan`, and a plan holds no time.

### From the prototype

The design keeps prototype b618's line edit, its trailer order, the fresh-id loop, `order` one above the largest, and the empty commits for several tasks. It drops `Commit.Show` and `git diff --no-index` for the tree diff; the file map for `FileChange`; the `SelfReview` flag for step 6; `checkGate`'s scan of `gates.yaml` and `nextOrder`'s scan of task files for `Source`; and the local scalar decoder, since `old` comes from tablo. It settles the prototype's seven findings: the surface above; the subjects; no `Authorised:` on `propose` and an automatic `Reviewed:` on `record`; `Model:` from an option or the environment; the refusals of the last table; `order` appended, references offered, junctions not; and Git's diff as the shown form.

## Conformance to the texts

- **SYNTAX.md, Commit trailers.** One trailer per task per line; task trailers, then `Model:`, then `Co-Authored-By:`, in one final paragraph, as its second example orders them.
- **README.md, Status.** `record` covers the four status rules (steps 2 and 3), the self-review sentence (step 6), the hand-off (step 4) and the recursive file that holds only the gate; `reaffirm` and `review` make the two empty commits the section shows.
- **README.md, Proposed and authorised tasks.** `propose` is the first way to authorise and `authorise` the third and fourth. The second, `git merge --no-ff`, stays Git's: no command merges.
- **Two places where the texts differ.** README.md's History finds trailers with `git log --grep='^Reviewed: 9f31 '`, which matches a line anywhere in a message; SYNTAX.md places a trailer among the trailers. The design follows SYNTAX.md (step 6), and `body-trailer` keeps the two readings equal for every commit a command makes. SYNTAX.md's trailer table says "the committer" accepts; README.md reads "author or committer". The design follows README.md (step 2).

## Decisions at review

The owner decided each question this design raised on 2026-10-06, together with the cross-design rulings of that review; a decision the review did not reach stands as the design states it, accepted with the design.

1. **The package.** Accepted with the design, as stated: `github.com/nbyoung/tabloio/action`, imported by tablotui as Go, with `Plan` as the dry-run form. The alternative runs the `tabloio` binary with `--dry-run` and parses its text, which decouples the releases and loses the typed plan and refusals. Binds `518e`, whose task file now requires this one from implementation to implementation.
2. **tablo as an executable**, behind `Source`. Decided by the owner on 2026-10-06, for the alternative: every front end links tablo's library (4ed9 decision 1, 5ca9 decision 1), so `Tablo` is an in-process `Source`, `--tablo` goes, and nothing else here changes, as A8 foresaw. The facts the package asks for are those the envelope carries, under one subcommand per view, `gates`, `task <id>` and `history` (4ed9 decision 3); A3, A4 and T29 read so.
3. **Refuse, with no override.** Accepted with the design, as stated: `review` and `authorise` refuse a hand the method would not read, and `record` refuses a status the validator rejects. The alternative warns and commits, as the method itself is audit-only; a user who wants that commit makes it with `git commit --trailer`.
4. **`record` reviews by itself.** Accepted with the design, as stated: when the hand that records holds the reviewer of a junction the status passes, the commit carries `Reviewed:` with no option, and the plan shows it. The alternative is a `--review` option, as the prototype had. `propose` likewise never writes `Authorised:`. README.md now also states the step this command serves: after the reviewer's `Reviewed:` commit, the contributor records the gate.
5. **The agent's trailers.** Accepted with the design, as stated: `--model` and `--co-author`, defaulting to `TABLOIO_MODEL` and `TABLOIO_CO_AUTHOR`; no Git configuration key. The alternative names are `TABLEAUX_MODEL` and `TABLEAUX_CO_AUTHOR`, shared by every tool of the family. Binds `e4c7`, `518e`.
6. **`--yes` off a terminal.** Accepted with the design, as stated: without a terminal the command commits only with `--yes`. The alternative commits when stdin is not a terminal, which an agent's shell would trigger unseen.
7. **`authorise` on the trunk alone.** Accepted with the design, as stated: it refuses on any other branch and when the trunk is undetermined. The alternative allows a branch that later fast-forwards onto the trunk, where the trailer does count.
8. **The junction a commit is at** (the open point of audit H3 and H6). Decided by the owner on 2026-10-06: a commit that changes a status's gate is at the junction of the gate it records; any other status commit, and a `Reaffirmed:`, is at the task's next applicable junction. README.md states it under Junctions, beside the trailer sentences RULES.md cites. The alternative read every status commit at the next junction, which charges the work of a gate to the gate after it. Binds tablo `dada` and `8ed1`, tabloio `e4c7` and `9167`, tableaud `9a9c`.
9. **Pins ride on `record`.** Accepted with the design, as stated: `record <id> --pin` commits the moved gitlink, alone or beside the gate; no sixth command. The alternative is `tabloio pin <id>`. The method states no rule that the subproject's task has completed before the parent's gate advances, so the command checks none.
10. **The default subjects**, with the id in parentheses after the title. Accepted with the design, as stated. The alternative leaves the id to the trailer and the diff, as this project's own subjects do.
11. **Exit codes.** Accepted with the design, as stated: 1 for a refusal and a declined prompt, 3 for a commit Git or a hook rejects. The alternative gives a refusal its own code, apart from tablo's "an error diagnostic".
12. **The plan.** Decided by the owner on 2026-10-06: this task's file now requires `5ca9` from implementation to implementation, since both land in one command table (5ca9 decision 10). The cross-project requirements on tablo's `4ed9`, `8118` and `493e` at integrate wait in this paragraph until the commits they must name exist, as README.md now allows; the umbrella's requirement of tabloio on tablo states the dependence meanwhile. The person parameter is `--person` (4ed9 decision 2).
13. **What the designs accepted on 2026-10-07 settle here.** Recorded on 2026-10-07 from tablo's `8118` and `27a3` and tablotui's `518e`, which the owner accepts that day.
