# Design 1422: Snapshot workflow

A reusable CI recipe validates a Tableaux project on every push and regenerates `STATUS.md` on the trunk, and a pre-commit hook validates the staged project before a commit lands. The recipe and the hook run the released `tablo` and `tabloio` binaries; neither needs Go (D1). The drafts under [`1422/`](1422/) fix the shape; the implementation turns them into files at the paths below.

| Draft                                    | Lands as               | Holds                                                           |
|------------------------------------------|------------------------|-----------------------------------------------------------------|
| [`1422/action.yml`](1422/action.yml)     | `snapshot/action.yml`  | The composite action: inputs and three steps                    |
| [`1422/snapshot.sh`](1422/snapshot.sh)   | `snapshot/snapshot.sh` | The logic of each step: `install`, `validate`, `render`, `commit` |

## The CI recipe

### Form

A composite action at `snapshot/` in this repository, versioned by tabloio's own release tags. A composite action, not a reusable workflow, because the action's files travel with it: the steps call `$GITHUB_ACTION_PATH/snapshot.sh`, which the harness also tests alone. A reusable workflow runs in the caller's checkout and cannot reach its own scripts at its own ref. The price is that the consumer writes the triggers, the checkout and the permissions, about fifteen lines, which the README gives:

```yaml
# .github/workflows/tableaux.yml in a consumer project
name: Tableaux
on:
  push:
  pull_request:
permissions:
  contents: write
concurrency:
  group: tableaux-${{ github.ref }}
jobs:
  snapshot:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0          # history: authorisation, reviews, dates
          submodules: recursive   # pins: recursive junctions read subprojects
      - uses: nbyoung/tabloio/snapshot@v0.2.0
```

### Inputs

| Input             | Default                          | Meaning                                                      |
|-------------------|----------------------------------|--------------------------------------------------------------|
| `project`         | `.`                              | The directory that holds `.tableaux`                         |
| `output`          | `STATUS.md`                      | The file the snapshot writes                                 |
| `view`            | `tableau --level glance`         | The tabloio arguments that render it, for example `tableau --level detail` |
| `trunk`           | The repository's default branch  | The branch whose pushes regenerate the snapshot              |
| `tabloio-version` | The tag the action runs at       | The tabloio release to install                               |
| `tablo-version`   | The tablo version tabloio builds against | The tablo release to install                         |

**The default level.** `STATUS.md` renders the global tableau at glance: the root and its children, each with its derived status, as VIEWS.md gives every role on a static export. The short table shows the project's architecture, one row per branch, so a new contributor finds the branch that matches their own interest and follows its link into the plan; every row of a large plan would bury that. The default states the level in full, so the snapshot does not change if tabloio's own default does. A project that wants every row sets `view` to `tableau --level detail`.

The defaults pair the three versions: `@v0.2.0` installs tabloio v0.2.0, and that binary names the tablo release it links, so validation and rendering agree on the language version. A consumer that calls the action at a branch or a SHA sets `tabloio-version`; `install` refuses a ref that is not a tag.

### Binaries

`install` downloads `<tool>_<version>_<os>_<arch>.tar.gz` and `checksums.txt` from the GitHub release, the names GoReleaser writes from `.goreleaser.yaml`, checks the archive's SHA-256, and extracts the binary into `$RUNNER_TEMP/tableaux-bin` on the path. It uses `curl` and `shasum`, which Linux and macOS runners carry, and no token, since the releases are public. A checksum mismatch or a missing asset fails the step.

**Two binaries.** The recipe installs both tools, and `validate` stays a command of tablo alone: tabloio does not pass it through. The recipe and the hook then depend on one contract for the flags, the exit codes and the diagnostics (A1 to A5), tablo stays the plumbing as PLAN.md divides it, no front end gains a second entry to the validator, and a project takes a validator fix without a tabloio release. The price is one more download in CI, which the action makes without the consumer's help. The hook validates only, so it needs `tablo` alone.

### Every push and pull request: validate

`tablo -C <project> validate --json` runs at the checked-out commit. Each diagnostic becomes a GitHub annotation at its file, line and column, errors as `::error` and warnings as `::warning`. An error diagnostic fails the job; warnings alone pass it.

### The trunk only: regenerate

The regenerate step runs only on a `push` to `trunk`, after validation passes. `render` writes `tabloio -C <project> <view> --markdown` to `output`. `commit` then:

1. Stages `output` and stops with no commit when it is unchanged. Rendering is deterministic, so a push that changes nothing the view shows changes nothing here.
2. Commits `output` alone as `github-actions[bot] <41898283+github-actions[bot]@users.noreply.github.com>`, author and committer, with the subject `Regenerate STATUS.md` and a body line naming the tabloio version and the source commit.
3. Pushes `HEAD` to `refs/heads/<trunk>`. The push fast-forwards only if the trunk still stands at the source commit. When it is rejected because the trunk moved, the step exits 0 with a notice: the run for the new head renders a newer snapshot. Any other rejection fails the step.

**No commit id in the snapshot.** `STATUS.md` does not name the commit it reflects; the commit body does. Most viewers read the file inside the repository, where the latest `STATUS.md` means the latest committed status, and a commit id in the file would change it on every push and so commit on every push, which breaks the fixed point of step 1.

**Trailers.** The commit carries none. SYNTAX.md's trailers each record an act on a task (`Authorised:`, `Reviewed:`, `Reaffirmed:`) or the model that ran (`Model:`); a snapshot does neither and touches no file under `.tableaux`, so the history derives no event from it and the audit sees no agent work.

**Loop avoidance.** A push made with `GITHUB_TOKEN` triggers no workflow, so the snapshot commit starts no run. If a consumer pushes with another token, the run it starts renders the same file and stops at step 1: the fixed point ends the loop in one round.

**Permissions.** The job needs `contents: write` for the push. A pull request from a fork receives a read-only token, and the regenerate step never runs on a pull request.

**A protected trunk.** A trunk that requires pull requests rejects a push made with `GITHUB_TOKEN`. The project then gives the checkout step a credential that the trunk's protection lets bypass, and the action stays unchanged: `commit` pushes with whatever credential the checkout leaves in place, so the action takes no `token` input. A repository admin stores the credential once as a secret and adds it to the bypass list once; no contributor does anything after that. The project picks the credential that suits it, and the README gives both variants:

```yaml
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
          submodules: recursive
          token: ${{ steps.app.outputs.token }}       # a GitHub App installation token, or
          # ssh-key: ${{ secrets.TABLEAUX_DEPLOY_KEY }} # a deploy key with write access
```

An app serves many repositories of one organisation; a deploy key serves one repository and needs no app. A personal access token also works but ties the snapshot to one person's account. A push with any of these starts a workflow run, which renders the same file and stops at step 1, as Loop avoidance states. An unprotected trunk needs no credential: `GITHUB_TOKEN` pushes.

The recipe does not regenerate through a pull request. The action can open one, but a person must still merge it, a pull request opened with `GITHUB_TOKEN` starts no runs and so cannot meet required checks without a second credential, and every status-changing push adds a pull request and a merge commit.

**Concurrency.** The consumer's `concurrency` group queues trunk runs one at a time; GitHub drops a queued run that a newer one replaces, and the newest renders the newest trunk.

### When validation fails

The job fails red on the push and on the pull request, with annotations at the offending lines. The regenerate step does not run, so `STATUS.md` stays at the last valid trunk commit, and the next valid push brings it current. The snapshot never shows an invalid plan.

## The pre-commit hook

**Install.** `hooks/pre-commit` is a POSIX shell script in this repository and in each release archive. A user copies it into place and puts `tablo` on the path:

```
curl -fsSL -o .git/hooks/pre-commit https://raw.githubusercontent.com/nbyoung/tabloio/v0.2.0/hooks/pre-commit
chmod +x .git/hooks/pre-commit
git config tableaux.project sub/dir   # only when .tableaux is not at the root
```

The copied script is the only install this task builds. It asks for `tablo` alone, as the hook does, and it costs nothing beyond the script; the hook is a convenience and not the guard, since the recipe validates every push. Git installs no hook on clone, so each contributor copies it once per clone, and one copy covers every worktree of that clone. A clone that already has a pre-commit hook merges the two by hand. Two other installs wait:

- A `.pre-commit-hooks.yaml` for the pre-commit framework, which a team commits once and which chains with other hooks, waits until a project asks: it brings Python to each contributor, and it expects `tablo` on the path all the same.
- A `tabloio hook install` subcommand, which detects an existing hook and ships the script inside the binary, falls outside this task: it makes tabloio a requirement of a hook that runs only `tablo`, and if it proves wanted it belongs with the Write commands task (b618).

**What it validates.** The staged tree. `git write-tree` turns the index into a tree object, and `tablo --ref <tree> validate` reads the files through `git ls-tree` and `git cat-file`, so an unstaged fix does not pass a broken commit and an unstaged break does not block a good one. The hook prints tablo's diagnostics and fails the commit on an error.

**Speed.** A commit that stages nothing under `.tableaux` costs one `git diff --cached` and runs no validator. Otherwise it costs `git write-tree` and one `tablo` run, whose startup is milliseconds (PLAN.md, Why Go); the target is under 200 ms on the Tableaux tooling plan.

**Submodule pins.** A commit that stages only a moved pin stages nothing under `.tableaux`, so the fast path skips it, as Git itself records a pin without reading the submodule. The recipe checks out the submodules and validates every push, so CI reports what a moved pin breaks: a `commit` field that no longer equals the pin (J17), a pin off the subproject's trunk (J13), or a cross-project requirement whose task the new pin lacks. The hook then never fails because a clone has not fetched the commit a pin names. A commit that stages a change under `.tableaux` beside a moved pin is validated; what tablo reads of the subproject at the staged pin, and what it reports when the clone lacks that commit, stays with tablo's Validator (8118).

**Bypass.** `git commit --no-verify`, as with any hook. Without `tablo` on the path the hook fails and says so, naming the bypass.

## Assumed interfaces

These are assumptions, not facts; the Read commands task (5ca9) and tablo's Plumbing command (4ed9) and Validator (8118) confirm or amend them at their design gates.

| # | Of      | Assumption                                                                                                   |
|---|---------|--------------------------------------------------------------------------------------------------------------|
| A1 | tablo  | `tablo [-C dir] [--ref ref] validate [--json]`, the shape prototype 4ed9 shows                              |
| A2 | tablo  | `--ref` takes any tree-ish, including a bare tree id from `git write-tree`, since validation reads files only and no history |
| A3 | tablo  | `-C` names a project directory below the repository root, and `--ref` reads `.tableaux` at that path in the tree |
| A4 | tablo  | Exit 0 on no error diagnostic, 1 on an error diagnostic, 2 on usage, 3 on a failure to read (4ed9)          |
| A5 | tablo  | The JSON envelope's `diagnostics` each carry `severity`, `code`, `path` relative to the project, `line`, `col` and `message`; 8118 shows the positions |
| A6 | tablo and tabloio | Releases publish `<tool>_<version>_<os>_<arch>.tar.gz` and `checksums.txt`, as tabloio's `.goreleaser.yaml` does today |
| A7 | tabloio (5ca9) | `tabloio [-C dir] tableau --level glance --markdown` writes the global tableau at that level to stdout and never changes project state; each row links its task to a file in the repository, as the Renderers task (1093) states |
| A8 | tabloio (5ca9) | The output is deterministic: the same files and history give the same bytes, with no time of rendering and no commit id unless a flag asks |
| A9 | tabloio (5ca9) | `tabloio version` prints one line, and `tabloio version --json` names the tablo version it links as `data.tablo` |
| A10 | GitHub | A ruleset's bypass list accepts a GitHub App and a deploy key; the implementation confirms it for both before the README offers them |

## Tests

The implementation adds a shell harness, `snapshot/test.sh`, that CI runs beside `go test`. It builds throwaway repositories under a temporary directory, a bare `origin` and clones, and puts stub `tablo` and `tabloio` scripts first on the path; a stub logs its arguments and fails when the tree at `--ref` holds a marker. `TABLEAUX_RELEASES` points `install` at a `file://` directory of fixture archives. `actionlint` checks `action.yml` and the consumer example.

| # | Proves                                                                   | How                                                                                      |
|---|--------------------------------------------------------------------------|------------------------------------------------------------------------------------------|
| T1 | `install` fetches the right archive for the host and puts the binary in `bindir` | Fixture archives for each os and arch; run and call the binary                          |
| T2 | `install` fails on a checksum mismatch, a missing asset or a non-tag ref | Corrupt one fixture, remove one, pass `main`; exit non-zero, nothing installed            |
| T3 | `validate` turns diagnostics into annotations with file, line and column | Stub emits an error and a warning; compare stdout                                        |
| T4 | `validate` fails on an error and passes on warnings alone                | Stub exit codes 1 and 0                                                                   |
| T5 | `commit` commits a changed snapshot as the bot, touching `output` alone, with no trailer | Change the stub's output; inspect `git log --format`, `git show --stat` and `git interpret-trailers --parse` |
| T6 | `commit` makes no commit when the snapshot is unchanged (the fixed point) | Render twice; the commit count holds                                                    |
| T7 | `commit` exits 0 without a commit on the trunk when the trunk moved        | Push from a second clone between render and commit                                       |
| T8 | `commit` fails when the push fails for another reason                    | A read-only origin                                                                        |
| T9 | `render` failure leaves `output` untouched and fails the step            | Stub `tabloio` exits 1                                                                    |
| T10 | The hook skips validation when nothing under `.tableaux` is staged      | Stage another file; the stub logs no call                                                |
| T11 | The hook validates the staged tree, not the working tree                | Four cases: good and bad staged, each with the opposite in the working tree              |
| T12 | The hook fails, naming the bypass, when `tablo` is absent               | A path without the stub                                                                   |
| T13 | The hook honours `tableaux.project`                                     | A project in a subdirectory                                                               |
| T14 | The recipe works against the real binaries                              | Once tablo and tabloio release: the harness reruns T3, T5, T6 and T11 with the real tools on a corpus entry, and times the hook on the Tableaux plan against 200 ms |

The trunk-only condition, the permissions, the push to a protected trunk with a bypass credential and loop avoidance on GitHub itself fall to the validate gate: tabloio's own repository calls the action, and the owner sees one snapshot commit per changing push and no run from it, or one run that stops at the fixed point when a bypass credential pushes. `act` does not reproduce `GITHUB_TOKEN`'s trigger rules, so the design does not rely on it.

A trial of the drafts against stubs, outside the repository, already passes T6, T7, T10, T11 and T12 and the non-tag case of T2.

## Open questions for the owner

1. **Branch protection.** Decided by the owner on 2026-10-02: the project supplies a bypass credential, a GitHub App token or a deploy key, on the checkout step, as [A protected trunk](#the-trunk-only-regenerate) states. The recipe does not regenerate through a pull request.
2. **Level and columns.** Decided by the owner on 2026-10-02: the default `view` renders at glance, as [The default level](#inputs) states, so that the architecture a new contributor reads first matches their interest. The window keeps the default VIEWS.md gives the global tableau.
3. **A commit id in the snapshot.** Decided by the owner on 2026-10-02: the snapshot names no commit, as [No commit id in the snapshot](#the-trunk-only-regenerate) states and A8 assumes; the commit body names the source.
4. **One binary or two.** Decided by the owner on 2026-10-02: two binaries, with `validate` in tablo only, as [Two binaries](#binaries) states. Whether tabloio links tablo as a library or runs its executable for view data stays with the Read commands task (5ca9) at its design gate; either way the recipe installs both.
5. **Hook install.** Decided by the owner on 2026-10-02: the copied script, as [The pre-commit hook](#the-pre-commit-hook) states. The pre-commit framework manifest and the `tabloio hook install` subcommand wait.
6. **Submodule pins.** Decided by the owner on 2026-10-02: the hook skips a commit that stages only a moved pin, and CI catches what it lets through, as [Submodule pins](#the-pre-commit-hook) states.
7. **Windows runners.** The recipe supports Linux and macOS runners. Is Windows needed?
