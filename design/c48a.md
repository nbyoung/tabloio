# Design c48a: Structural renderers

This task renders the two views of who holds what: the authority delegation, a tree of tasks and assignees, and the task assignment, a section per email. Both stand on the architecture of [design e3ed](e3ed.md#the-shared-architecture): the packages, the input types, the document model, the Markdown writer, the page frame and the rules R1 to R17, which this document cites and does not repeat. Three choices are this task's own. The tree is a preformatted block of two columns that both indent, drawn by one rule that reproduces the three trees of the mockup to the byte. The renderer, not tablo, collapses the children of a parent in the tree at glance (D1). The assignment's tables hold one Task column and fold by the run rule, in place of the three fold rules the mockup uses (D2, D3).

## The model

The task adds `internal/render/authority.go` and `assignment.go`, two view structs in `internal/render/view/`, and fixtures and golden files under `internal/render/testdata/authority/` and `testdata/assignment/`. It exports nothing new: `render.Render` reaches the two builders through `view.Decode("authority", …)` and `view.Decode("assignment", …)`.

### The authority delegation

```go
// Delegation is the authority delegation view.
type Delegation struct {
	Head
	Rows     []DelegationRow `json:"rows"`     // every task in view, in display order
	Parents  []Chain         `json:"parents"`  // detail: every parent in view, in display order
	Deciding []Deciding      `json:"deciding"` // provenance: newest first
	Commands []Command       `json:"commands"` // provenance
}

// DelegationRow is one task of the tree.
type DelegationRow struct {
	TaskRef
	Depth     int    `json:"depth"`
	Assignee  string `json:"assignee"`
	Parent    bool   `json:"parent"`    // the task has children
	Delegated bool   `json:"delegated"` // its assignee differs from its parent's
	Proposed  bool   `json:"proposed"`
	Differs   bool   `json:"differs_from_trunk"` // off the trunk: the branch changes the file
}

// Chain is what one parent gives its subtree.
type Chain struct {
	TaskRef
	Assignee    string      `json:"assignee"`
	Authorities []Authority `json:"authorities"` // of its children, nearest first (design e3ed)
	Children    []string    `json:"children"`
	Defaults    []Default   `json:"defaults"` // the gates at which this parent states an entry
}

// Default is a junction entry a parent states, with each field resolved.
type Default struct {
	Gate string `json:"gate"`
	Marked
	Contributor     string `json:"contributor"`
	Model           string `json:"model"`
	Reviewer        string `json:"reviewer"`
	ContributorFrom string `json:"contributor_from"` // an ancestor's id when it supplies the field
	ModelFrom       string `json:"model_from"`
	ReviewerFrom    string `json:"reviewer_from"`
}

// Deciding groups the tasks one commit decides.
type Deciding struct {
	Commit Commit   `json:"commit"`
	Way    string   `json:"way"`    // change, merge, trailer
	Merged string   `json:"merged"` // a merge: the commit it brings in
	By     string   `json:"by"`     // author, committer, both, or empty
	Tasks  []string `json:"tasks"`
}
```

| Level      | Blocks, in order                                                                                                                  |
|------------|-----------------------------------------------------------------------------------------------------------------------------------|
| glance     | The tree, as a `Pre`; the count line `<n> tasks, <n> delegations, <n> authorised, <n> proposed.`                                    |
| detail     | The tree with no parent collapsed; the count line; `## Chains and defaults: n`, then one `###` section per parent                    |
| provenance | `## Deciding commits: n`: Commit, Date, Author, Committer, Accepts by, The authority is, Tasks; then the commands                    |

**The tree.** The first line reads `Task` and `Assignee`. A row prints two spaces per step of depth, the id, a space and the title; then spaces up to the assignee column; then two spaces per step of depth again and the assignee. The assignee column starts two characters past the longest task text among the rows drawn, counted in code points. Every row states its assignee, as the mockup draws it; the dot of the VIEWS.md example does not appear. After the assignee, two spaces and a word follow where one applies: `<n> children` on a collapsed parent, `proposed`, or `proposed (differs from trunk)`. Titles and emails print as they are, since a `Pre` escapes nothing. With `Links.Project` set the tree stays plain text: a code block holds no link, and the chains' headings carry the task links at detail.

**Collapsed children (R11).** At glance the builder hides the children of a parent when the parent has five or more, each is a leaf, each has the parent's assignee and none is proposed; the parent's row then carries `<n> children`. Detail, provenance and `Options.Unfold` draw every row. The count line counts tasks, hidden ones included.

**A chain's section** opens ``### `<id>` <title> · <assignee>`` and holds, as the draft shows: `Authorities of its <n> children, nearest first:` with the authorities grouped as design e3ed groups them; `Children:` with the ids; then the defaults table, Gate, Marks, Contributor, Model, Reviewer, with its key line (R2), or the sentence `` `<id>` states no junction defaults.`` A field that an ancestor supplies prints ``<value>, from `<id>` ``. An exempt gate prints `—` in Marks and no other cell, one row per gate.

**The deciding commits.** Accepts by reads `a change on the trunk`, ``a merge of `<merged>` `` or `an Authorised: trailer`. The authority is reads `the author`, `the committer`, `the author and the committer`, or stays empty for a proposed task. Tasks reads the count, a colon and every id.

**Parameters and empty forms.** With `--proposed` the data holds the proposed tasks and their ancestors, and the frame says `proposed only`; when none is proposed the sentence `**No task is proposed.**` stands in place of the tree and the count line follows. Off the trunk the frame says so (design e3ed, the page frame) and every row carries its word. The view marks no person: `person` selects rows, which tablo does. Related views, for the See also line: task, assignment, history, audit, queue.

### The task assignment

```go
// Assignment is the task assignment view.
type Assignment struct {
	Head
	People    []PersonRow     `json:"people"`    // one per email in view, in order of first appearance in the tree
	Recursive []string        `json:"recursive"` // tasks whose next junction is recursive
	Sections  []PersonSection `json:"sections"`  // detail: one per row of People
	Commits   []Commit        `json:"commits"`   // provenance: every commit a Stated names, newest first
	Commands  []Command       `json:"commands"`
}

// PersonRow is the glance of one email.
type PersonRow struct {
	Email           string   `json:"email"`
	Assigned        int      `json:"assigned"`
	ContributesNext int      `json:"contributes_next"`
	ReviewsNext     int      `json:"reviews_next"`
	Models          []string `json:"models"`
}

// PersonSection is what one email carries.
type PersonSection struct {
	Email       string         `json:"email"`
	Assigned    []AssignedRow  `json:"assigned"`
	Recursive   []RecursiveRow `json:"recursive"`
	Contributes []JunctionRow  `json:"contributes"` // gate order, then display order
	Reviews     []JunctionRow  `json:"reviews"`
	Models      []ModelRow     `json:"models"` // an agent: its models by gate
	Counts      []GateCount    `json:"counts"` // every gate, in order
	Authority   []Subtree      `json:"authority"`
	Positions   []Position     `json:"positions"` // provenance
}

type AssignedRow struct {
	TaskRef
	Under  string  `json:"under"` // the parent's id
	Status Status  `json:"status"`
	Next   *Marked `json:"next"`      // nil for a parent
	Gate   string  `json:"next_gate"`
}
type RecursiveRow struct {
	Task       TaskRef `json:"task"`
	Gate       string  `json:"gate"`
	Subproject SubRef  `json:"subproject"`
	Status     Status  `json:"status"` // of the subproject's task
}
type JunctionRow struct {
	Task        TaskRef `json:"task"`
	Gate        string  `json:"gate"`
	Contributor string  `json:"contributor"`
	Model       string  `json:"model"`
	Reviewer    string  `json:"reviewer"`
	When        string  `json:"when"` // passed, next, later
}
type ModelRow struct {
	Gate, Model, StatedBy string
	Junctions, Next       int
}
type GateCount struct {
	Gate                                                    string
	Standing, Contributes, ContributesNext, Reviews, ReviewsNext int
}
type Subtree struct {
	Task        TaskRef `json:"task"`
	Descendants int     `json:"descendants"`
}

// Position groups the tasks at which one source gives the email a position.
type Position struct {
	Kind     string   `json:"kind"` // assignee, authority, contributes, reviews, recursive
	Gate     string   `json:"gate"`
	Tasks    []string `json:"tasks"`
	Reviewer string   `json:"reviewer"`
	From     Stated   `json:"from"`          // the assignee, the authority, or the contributor and model
	RevFrom  Stated   `json:"reviewer_from"`
	URL, Pin string   // recursive
}

// Stated says where a field stands.
type Stated struct {
	By     string `json:"by"`     // a task id, or "default"
	Key    string `json:"key"`    // for example junctions.release
	File   string `json:"file"`
	Commit string `json:"commit"`
}
```

| Level      | Blocks, in order                                                                                                                                         |
|------------|----------------------------------------------------------------------------------------------------------------------------------------------------------|
| glance     | The table Email, Assigned, Contributes next, Reviews next, Models; when `Recursive` holds a task, the line `🪆 <n> tasks hand their next junction to a subproject: <ids>.`, its symbol the legend's `subproject` mark |
| detail     | Per email `## <email>`, with: `### Tasks assigned: n` (Task, Under, Status, Next junction) and its key line; `### No contributor in this project: n` (Task, Next gate, Subproject, Its root task stands at); `### Contributes: n junctions, m next` and `### Reviews: n junctions, m next`, each a run of gate groups; `### Models by gate` (Gate, Model, Stated by, Junctions, Next) for an agent; `### Counts by gate`; `### Authority` |
| provenance | Per email `## <email>, provenance` after the detail sections: the tables Position, Tasks, Stated in; Contributes at, Tasks, Contributor and model from, Reviewer, Reviewer from; Reviews at, Tasks, Reviewer from, Contributor and model from; Task, Stated in, Pinned at. Then `## Commits: n` (Commit, Date, Author, Committer) and the commands |

The draft fixes the detail form. The remaining rules:

- **A gate group** opens with a paragraph, `**<gate by R2>** · <n> junctions · <m> next`, and holds one table: Task, Model, Reviewer, When under Contributes; Task, Contributor, Model, When under Reviews. The builder groups the rows by gate in the legend's order and prints a group only for a gate that holds a row. Each table takes the run fold (R10).
- **Tasks assigned.** Status is the status phrase (R3). Next junction reads the gate (R2) and the marks; a parent's cell is empty.
- **Counts by gate** holds every gate of the legend, undefined included, and a last row `**Total**` in bold.
- **Authority** reads ``Over `<id>` <title> and its <n> descendants.``, one sentence per subtree, or `None.`
- **A `Stated`** prints as the task (R4), the key and the file in code spans and the commit (R6): `` `437e` Tableaux tooling, `junctions.release` in `.tableaux/tasks/437e.yaml`, commit `6b6c99a` ``; `default` prints `the plain default`.
- **Empty forms (R9).** A project always has an email, so the glance table has a row. A section's empty list prints its heading with `none`: `### Reviews: none`.
- **Parameters.** `person` selects one row and one section, as the second draft shows; the view marks no cell. Related views, for the See also line: queue, authority, task, tableau, context, blockage, history, audit.

### What the design keeps from the prototype

From `prototype/c48a` it keeps the tree as a code block, the word `proposed`, the right-aligned numbers and the sections after the tree. It drops the dot for a parent's assignee, the em dash for an absent value (R7), the header line that named the parameters (the frame replaces it), and the flat junction lists. The prototype's question whether the model check belongs in this view is settled: it does not; the audit and the task definition show it.

## Implementation notes

The task follows `e3ed` in time for the shared packages only: once `view`, `doc`, `markdown` and the rule helpers exist, it adds `authority.go`, `assignment.go`, `view/delegation.go`, `view/assignment.go` and its test data, and touches no shared file but the switch in `Render` and in `Decode`. The plan states no requirement between the four siblings; the order field of the parent places `e3ed` first, which is enough for one implementer, and a `requires` from `c48a`, `a3cc` and `9167` on `e3ed` at implementation would say it outright. `prototype/c48a/` stays until the unit gate passes, then goes. No dependency.

## Decisions at review

1. **The renderer collapses the tree, from five children.** At glance a parent hides its children when it has five or more, all leaves, all with its assignee, none proposed. The alternatives: tablo hides them by level, which fixes one fold for every front end, or the tree collapses whatever the number, which hides a parent's two children.
2. **One Task column in the assignment** (R4), and `next` in plain type. The alternative keeps the mockup's Task and Title columns and its bold `next`, and then bold means two things in a view with a person.
3. **The run fold in the assignment** in place of the mockup's rules (S8), under e3ed's decision 8: a group of eight alike rows folds, where the mockup shows all eight.
4. **Every gate in Counts by gate**, undefined included (S12). The alternative starts at the first gate after undefined, as the mockup does, and loses a task that has no status file.
5. **A default shows the resolved field and its source**, ``nbyoung@nbyoung.com, from `437e` ``, so that the marks and the cells of a row agree. The alternative shows only what the parent's own entry states, and a row then carries 👀 beside an empty Reviewer.
