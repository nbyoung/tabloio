# Design e4c7: Agent briefs

`tabloio queue --person <email> --brief <task> <gate>` writes the brief of one work item: plain text that a person pastes into an agent's prompt, or a harness passes to it, so that the agent does one junction's work and makes the right commit. Four choices shape it. The brief reproduces the block the approved mockup shows, in its six parts, as plain text at 76 columns, the same bytes under `--markdown` and `--text`. `tablo` emits everything the brief states about the plan in one `brief` object, and tabloio joins nothing. The tool adds fixed text for the three things every hand-written brief of this effort repeats: the commit identity, the trailer block and the hand-off. A project supplies its own standing text through junction `references`, which the brief names and does not inline, and the rest stays with the dispatcher.

The drafts under [`e4c7/`](e4c7/) fix the output. Each `.json` is the envelope the design assumes of `tablo`; each `.txt` is the brief it gives.

## What a brief carries

The three hand-written briefs of this effort (the mockup wave, tableaud's function wave, this design wave) run 99 to 144 lines and 8 to 12 kB each. Their parts fall into three sources.

| Part of a hand-written brief | Source | Where it lives |
|---|---|---|
| The task, its description and references, its place in the tree | The plan | Parts 1 and 2 of the brief |
| The gate and its criteria; the contributor, the model, the reviewer, and the task whose entry states each | The plan | Part 1 |
| The requirements, whether each is met, and what the work unblocks | The plan | Part 3 |
| The status the task stands at | The plan and the history | Part 4 |
| The status file the hand-off writes, line by line | The plan: the reviewer decides the form | Part 5 |
| The identity through `GIT_AUTHOR_*` and `GIT_COMMITTER_*`, and its check | Fixed text, with the contributor's email | Part 5 |
| The trailer block: one final paragraph, `Reviewed:` only where the agent reviews itself, the true model | Fixed text, with the junction's model and ids | Part 5 |
| Edit the status by hand; touch nothing else under `.tableaux` | Fixed text | Part 5 |
| What the gate asks for in this project: where a design, a prototype or a mockup goes, its form, the checks to run, the tools on the path, the prose style | The project's standing text | A file in the repository that a junction reference names |
| The worktree and the branch name; who else works at the same time; the points and questions specific to this run; the report the dispatcher wants; a cluster of several tasks for one agent | The dispatcher | The prompt, after the brief |

**Standing text.** The method already gives a junction `references` that "expand the gate's criteria for this task", and a junction entry on a parent is a default its subtree inherits. A project therefore states what it expects at a gate once: a file per gate in the repository, named in the root task's junction entry for that gate. Every brief under that root then carries the line `Junction reference: <url>, <text>   (<title>, <id>)` and the sentence that tells the agent to read it. The brief names the file and does not inline it: the agent reads it in its checkout at the commit it works from, the brief stays short, and tabloio reads no file of the project. Today no root task of the four projects states a junction reference, so every golden draft reads `Junction references: none`. A plain entry inherits field by field, so a child that states its own `references` at a gate replaces the inherited ones and must restate them.

**The dispatcher.** The brief ends at part 6 and takes no text from the dispatcher: no `--append`, no `--model`, no `--branch`. A person pastes their own lines after it; a harness concatenates. Part 5 says "on a branch off `main`" and leaves the name to the dispatcher. An agent that takes several tasks receives several briefs.

## The model

### The command

```
tabloio queue --person <email> [--ref <ref>] [-C <dir>] [-o <file>] --brief <task> <gate>
```

`--brief` selects the provenance level of one item and writes the brief as the whole output. The Read commands (5ca9) own the parsing, the call of `tablo` and the envelope (A8); this task adds what follows.

| Case | Standard output | Standard error | Exit |
|---|---|---|---|
| The item is work ready | The brief | Nothing | 0 |
| The item is work waiting | Nothing | `tabloio: <task> at <gate> waits and no brief starts it: <cause>` | 1 |
| The person has no work at that task and gate | Nothing | `tabloio: no work for <person> at <task> <gate>; tabloio queue --person <person> lists the items` | 1 |
| The `brief` object lacks a required field | Nothing | `tabloio: brief: <field> is missing in tablo's data` | 3 |
| `--brief` with `--level glance` or `--level detail`; a task that is not four lowercase hexadecimal digits; no gate | Nothing | Usage | 2 |
| `tablo` fails | Nothing | Its diagnostics | Its code |

`--markdown` and `--text` change nothing: the brief is plain text. A brief exists for work only. A waiting item gets none, "so that nobody starts" it; a review, an authorisation and a reaffirmation are one commit each, which the write commands (b618) make.

### The data

`tablo queue` with the brief parameter (one subcommand per view, named as the mockup files, as the owner ruled at review on 2026-10-06; this design was written against `tablo view work-queue`) returns the envelope of prototype 4ed9 with one object, `data.brief` (A1 to A7). The three `.json` drafts show it in full. tabloio decodes it into these types and reads nothing else.

```go
// Package brief writes the brief of one work item of the contributor work
// queue: the queue's provenance level for that item, as plain text.
package brief

// Data is data.brief of the queue view: one work item with every fact
// the brief states. Unknown fields are ignored.
type Data struct {
	Kind       string    `json:"kind"`       // "work ready" or "work waiting"
	Cause      string    `json:"cause"`      // why a waiting item waits
	Person     string    `json:"person"`     // whose queue holds the item
	Ref        Ref       `json:"ref"`
	Task       Task      `json:"task"`
	Gate       Gate      `json:"gate"`       // the gate the work reaches
	Junction   Junction  `json:"junction"`   // the junction, resolved
	Supplier   *Supplier `json:"supplier"`   // nil when the task's own entry or the default supplies the contributor
	Requires   []Edge    `json:"requires"`   // the task's requirements, in file order
	Dependents []Edge    `json:"dependents"` // the tasks that require this one, in display order
	Parent     *Parent   `json:"parent"`     // nil for the root
	Status     Status    `json:"status"`
}

// Ref is the commit in view. Name is the ref as the user gives it.
type Ref struct{ Name, Commit, Date string } // json: name, commit (40 hex), date (YYYY-MM-DD)

// Task is the task of the item. Path holds its ancestors, root first.
type Task struct {
	ID, Title, Description string
	References             []Reference
	Path                   []Link
}

// Gate is the gate with its legend. Follows is the kind of the task's next
// applicable junction after this gate: "plain", "recursive", or "" when the
// gate is the task's last applicable gate.
type Gate struct{ Key, Symbol, Name, Criteria, Follows string }

// Junction holds the resolved fields, each with the entry that supplies it.
type Junction struct {
	Contributor, Model, Reviewer Field       // Model.Value is "" for a person; Reviewer.Value is "" when no one reviews
	References                   []Reference // each with its Source
}

// Field is one resolved value and its source.
type Field struct {
	Value  string
	Source Source
}

// Source names where a field resolves from. Kind is "task" (an entry of
// the task ID, Title), "assignee" (a reviewer the method gives an agent) or
// "default" (the plain default).
type Source struct{ Kind, ID, Title string }

// Reference is a reference of a task or of a junction.
type Reference struct {
	URL, Text string
	Source    Source // set on a junction reference
}

// Link names a task.
type Link struct{ ID, Title string }

// Supplier is the task whose entry supplies the contributor.
type Supplier struct{ ID, Title, Description string }

// Edge is one requirement, seen from either end. URL and Commit are set on
// a cross-project requirement. Condition is the key VIEWS.md names.
type Edge struct{ ID, Title, From, To, Text, Condition, URL, Commit string }

// Parent is the task's parent with the tasks that require it.
type Parent struct {
	ID, Title  string
	Dependents []Edge
}

// Status is the task's status with its symbols, its deciding commit and
// the path of its file from the repository root.
type Status struct {
	Path, Gate, GateSymbol, State, StateSymbol, Reason, ReasonSymbol string
	Note, Date, Recorder, Commit                                     string
}
```

Every field takes the snake-case JSON key of its name (`gate_symbol`, `state_symbol`, `reason_symbol`); the drafts are the authority.

```go
// Request names the item a brief is asked for.
type Request struct{ Person, Task, Gate string }

// Decode reads the envelope's data and returns its brief. It returns a
// *NoWorkError when data holds no brief object, and an error that names the
// field when task.id, gate.key, junction.contributor.value, status.path or
// ref.commit is empty.
func Decode(data []byte, req Request) (Data, error)

// Render writes the brief of d to w. It returns a *WaitingError and writes
// nothing unless d.Kind is "work ready". The same d gives the same bytes.
func Render(w io.Writer, d Data) error

// NoWorkError says the person's queue holds no work at the task and gate.
type NoWorkError struct{ Person, Task, Gate string }

// WaitingError says the work waits, with its cause.
type WaitingError struct{ Task, Gate, Cause string }
```

The two `Error` methods return the messages of the table above without the `tabloio: ` prefix. The unexported surface is `wrap(text string, indent int) []string`, `fold(edges []Edge) [][]Edge`, `way(d Data) string`, `sourceLabel(s Source, taskID string) string` and `short(commit string) string`. The package lives at `internal/brief/` and imports the standard library only.

### The text

[`e4c7/brief.py`](e4c7/brief.py) states every rule of the text as code, in under 300 lines; the rules below are the same in prose.

**Layout.** UTF-8, lines end in LF, no line ends in a space, and the text ends in one newline. A title line, a lead paragraph, then six parts, each a heading `<n>. <name>` at column 0 with a blank line after it and before the next. Body text takes an indent of two spaces, a nested list or a literal block four.

**Wrapping.** `wrap` splits a paragraph on white space and fills greedily: a word joins the line while the line's length in runes, indent included, stays at or under 76. A blank line in a description ends a paragraph. Four kinds of line are never wrapped, so that a reader copies them whole: the rows of part 1, a reference line, a line of a literal block (the status file, the exports, the trailers), and a command of part 6. Width 76 is the width at which the generator reproduces the mockup's line breaks.

**The lead.** `on <name> at <hash>` names the ref and the first seven digits of its commit. When the name is `HEAD` or a prefix of the commit, the lead reads `at <hash>` and part 5 reads "a branch off `<hash>`".

**Part 1, the item.** Rows `Task`, `Gate`, `Contributor`, `Model`, `Reviewer`, the label padded to 13 columns. The three junction values pad to the longest of them, then three spaces, then the source: `(<title>, <id>)` for another task's entry, `(this task)` for the task's own, `(the assignee; the junction states none)` for a reviewer the method gives an agent, `(the assignee, by default)` for the plain default. A person has no `Model` row and no model paragraph; a junction nobody reviews reads `Reviewer     none`.

**Part 2, the task.** The description; one `Reference: <url>, <text>` line per reference, or `References: none`; one `Junction reference:` line each with its source and then the sentence "A junction reference expands the gate's criteria for this task. Read each one before you start.", or `Junction references: none`; `Under:` with the ancestors' titles, root first, joined by ` › `, and no such line for the root; then the supplier's paragraph, `<title> (<id>), whose entry sends this work to you: <description>`, when another task's entry supplies the contributor.

**Part 3, the requirements.** One `Requires:` line per requirement, of any gate, since the `from` and `to` say which gate it binds; a cross-project one reads `<id> <title> in <url> at <hash>`. A dependent whose `from` is the brief's gate is what this junction unblocks: `Unblocks: <id> <title> at <to>, <text>`. Every other dependent reads `Also required by: … from <from> to <to>, <text>: <condition>`. The parent's dependents at this gate follow under `Its parent <id> <title> at <gate> is required by:`. The empty forms are `Requires: nothing`, `Unblocks: nothing; no task requires <id>` and `Unblocks: nothing at this gate`.

**Part 4, the status.** One head line, symbols and keys, date, recorder, short hash, then the note on a line of its own.

**Part 6, the commands.** The two commands, with the short hash as the ref, so that they reproduce the brief after the branch moves.

### The commit, by junction

Part 5 depends on the resolved junction alone. `way` takes the first row that holds.

| Junction | Status file | Trailers | Who merges |
|---|---|---|---|
| The gate is `defined` | `gate: defined`, `state:`, `note:` | `Model:`, `Co-Authored-By:` for an agent | The dispatcher |
| A reviewer other than the contributor | The gate the status stands at, `state: nominal`, `reason: review`, `note:` | `Model:`, `Co-Authored-By:` for an agent | The reviewer, who passes the gate with `Reviewed: <id> <gate>` |
| The reviewer is the contributor | `gate: <gate>`, `state:`, `note:` | `Reviewed: <id> <gate>` on the commit that changes the status file, above `Model:` and `Co-Authored-By:` | The dispatcher |
| No reviewer: a person contributes and the junction states none | `gate: <gate>`, `state:`, `note:` | None | The dispatcher |

Where the agent records the gate, `state:` reads `nominal`, or `complete` when the gate is the task's last applicable gate, and the file holds `gate:` alone when the next junction is recursive, as README.md#status prescribes. The trailers are placeholders the agent fills: `Model: <the identifier your harness reports, matching <model>>`, since only the agent knows what ran, and `Co-Authored-By: <your model's display name> <<contributor>>`. The identity block exports the contributor's email as author and committer and shows the `git log` line that checks it; a person's brief has neither that block nor a trailer, unless the person reviews their own gate.

## Conformance to the texts

**VIEWS.md, "Contributor work queue" and "The brief".** The six parts hold what the text lists, in its order. The brief is the provenance level of one item; glance and detail belong to the Status renderers (a3cc). The view takes no window.

**The mockup, `docs/mockups/queue.md`, "Provenance: the brief".** For `c74a` at `mockup` the generator reproduces the mockup's block byte for byte from the title to the end of part 4, and part 6. Part 5 departs from it in four places, which Decision 4 lists: the mockup names the deliverable, `docs/mockups/queue.md`, which no plan data states, so the brief says "your work"; the brief adds the sentence on editing the status by hand; it adds the identity block; and it says "one final paragraph of trailers, with no blank line between them and nothing after them". Each addition answers a failure the first waves record: a commit under the owner's identity, a task file a YAML library rewrote, a `Reviewed:` trailer a blank line left unparsed.

**Where the texts do not settle the commit.** The design follows SYNTAX.md and README.md#junctions and names each place.

1. README.md#status says a contributor "who is also the reviewer, as an agent is at a junction that states none" carries `Reviewed:`. README.md#junctions gives that agent the assignee as reviewer, so the agent reviews itself only where the assignee is the agent's own email. The brief follows the junction rule: it compares the resolved reviewer with the contributor.
2. SYNTAX.md's example commit carries `Reviewed: c07d unit` with `Model:` and `Co-Authored-By:`, while the reviewer of `c07d` at `unit` is Ben. That commit counts only under Ben's identity. The brief never tells an agent to commit as the reviewer.
3. SYNTAX.md calls `Co-Authored-By:` the trailer an agent leaves "when it commits under a person's identity"; VIEWS.md and every wave put it on every agent commit. The brief follows VIEWS.md.
4. README.md counts a `Reviewed:` commit "authored or committed by the reviewer"; SYNTAX.md's table says "the committer". The brief sets both to the contributor, so a self-review holds under either reading.
5. No text says who writes the status that names the gate after the reviewer's `Reviewed:` commit. In this effort the agent does, in a second run. The brief keeps the mockup's sentence and stops at the hand-off.
6. "A commit at a junction" has no definition, so the brief asks for the trailers on every commit of the run.
7. `defined` passes by authorisation "whoever its reviewer is". No text says what a contributor records at `defined` for a task that is still proposed; the brief treats it as any other.
8. VIEWS.md names the conditions met, due and unmet without defining them, and prototype 493e emits `pending`. The brief prints the key `tablo` gives.

## Decisions at review

The owner decided each question this design raised on 2026-10-06, together with the cross-design rulings of that review; a decision the review did not reach stands as the design states it, accepted with the design.

1. **Plain text, one form.** Accepted with the design, as stated: the brief is the mockup's plain-text block, identical under `--markdown` and `--text`. The alternative is a Markdown document with headings, as the prototype writes and the task description says. Binds a3cc and e0f7.
2. **One `brief` object from `tablo`.** Accepted with the design, as stated: `tablo` derives every fact of the brief once, and tablotui and tableaud read the same object; tableaud's 44bf decision 2 asks the same. The alternative is that each front end joins the queue, two task views and the gate view. Binds tablo's `886d`, tablotui's `0afa` and tableaud's `44bf`.
3. **Work ready only.** Accepted with the design, as stated: a waiting item gives exit 1 and its cause; the other kinds have no brief. The alternative writes a brief that says "do not start", as the prototype does.
4. **Part 5 beyond the mockup.** Accepted with the design, as stated: "Your work" for the deliverable, the hand-edit sentence, the identity block and the stricter trailer sentence. The alternative keeps the mockup's part 5 and leaves all four to each project's standing text.
5. **Standing text through junction references.** Accepted with the design, as stated: a project keeps a file per gate and names it in its root task's junction entries; the brief names it and does not inline it. For this effort that means a `docs/gates/<gate>.md` in each repository and a `references` field on nine junction entries of each root, which is the owner's change to the plan and waits for it. The alternative is a flag that inlines a file.
6. **The command spelling.** Decided by the owner on 2026-10-06: `--person`, not `--for`, and `--brief <task> <gate>` as two arguments, as VIEWS.md and the mockup write (4ed9 decisions 2 and 3, 5ca9 decision 6). The tablo command is `tablo queue`, one subcommand per view named as the mockup file, where this design wrote `tablo view work-queue`; the text and A1 read so. Binds 5ca9, every renderer that prints a command, and tabloio's README, which now changes.
7. **`Co-Authored-By:` takes the contributor's email.** Accepted with the design, as stated: the mockup prints `noreply@anthropic.com`, which is this plan's contributor and no other project's. The alternative keeps the literal.
8. **The agent fills in `Model:`.** Accepted with the design, as stated: the brief holds a placeholder and takes no `--model`. The alternative lets the dispatcher state the identifier it spawned.
9. **No cap on length.** Accepted with the design, with the fold's threshold as ruled: the brief never truncates a text of the plan; only a run of more than eight dependents alike but for the task folds, the one long-list rule of tabloio (e3ed decision 8).
