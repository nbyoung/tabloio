# Design 9167: Temporal renderers

This task renders the two views that read the history: the history itself, one line per commit and task in author-time order, and the audit, one line per disagreement between the files and the history. Both stand on the architecture of [design e3ed](e3ed.md#the-shared-architecture) and cite its rules R1 to R17; the count helper comes from [design a3cc](a3cc.md#the-model). Three choices are this task's own. A line of the history holds the events one commit makes on one task, as the mockup and VIEWS.md draw it, and tablo merges them, not the renderer (A1). A long range folds by day at glance and nowhere else (D1). A finding arrives grouped, with the tasks one rule hits at one gate for one reason, and worded by tablo; the renderer lays it out and words nothing about a rule (D3).

## The model

The task adds `internal/render/history.go` and `audit.go`, `view/history.go` and `view/audit.go`, and test data under `testdata/history/` and `testdata/audit/`. It exports nothing new.

### The history

```go
// History is the history view.
type History struct {
	Head
	Subject  *TaskRef    `json:"subject"`  // the task parameter; nil for the whole project
	Lines    []Line      `json:"lines"`    // oldest first
	Events   int         `json:"events"`
	Commits  int         `json:"commits"`
	Kinds    []KindCount `json:"kinds"`    // task, authorised, status, reaffirmed, reviewed, pin (design a3cc)
	Days     []Day       `json:"days"`     // one per day that holds a line
	Commands []Command   `json:"commands"` // provenance: the git log commands that give the list
}

// Day counts one day's events.
type Day struct {
	Date    string      `json:"date"`
	Events  int         `json:"events"`
	Commits int         `json:"commits"`
	Kinds   []KindCount `json:"kinds"` // the kinds that occur, in the fixed order
}

// Line is what one commit does to one task.
type Line struct {
	Date     string   `json:"date"`
	By       string   `json:"by"`
	Kinds    []string `json:"kinds"`
	Task     TaskRef  `json:"task"`
	Proposal bool     `json:"proposal"` // off the trunk: the branch adds the event
	Status   *Status  `json:"status"`   // status, reaffirmed: what the event records
	Gate     string   `json:"gate"`     // reviewed
	Pin      *PinMove `json:"pin"`      // pin (design e3ed); Old is empty when the linkage first appears

	After        *Status    `json:"after"`           // detail from here: the task's status after the event
	Unchanged    bool       `json:"unchanged"`
	SubjectAfter *Status    `json:"subject_after"`   // a subtree: the subject's status after the event
	Effect       string     `json:"effect"`          // one of the keys below, or empty
	Model        string     `json:"model"`           // the Model: trailer
	Stated       string     `json:"stated"`          // the model the junction states
	StatedGate   string     `json:"stated_gate"`
	Reading      string     `json:"reading"`         // agrees, differs, missing, exempt, or empty
	Committer    string     `json:"committer"`       // only where it differs from By
	Sub          *SubEvents `json:"subproject"`      // pin: the subproject's own events between the commits

	Commit   *Commit   `json:"commit"`   // provenance
	Commands []Command `json:"commands"` // provenance: what reproduces this line
}

// SubEvents is a subproject's history between two pins.
type SubEvents struct {
	URL     string `json:"url"`
	Events  int    `json:"events"`
	Commits int    `json:"commits"`
	Lines   []Line `json:"lines"` // glance fields, and Model; empty when tablo folds them to the count
}
```

| Level      | Blocks, in order                                                                                                                         |
|------------|------------------------------------------------------------------------------------------------------------------------------------------|
| glance     | The count line; the day table (Day, Events, Commits, Kinds) when the lines span three days or more; the line table (Date, By, Event, Task, Gate and state, or pin) |
| detail     | The count line; per day a heading and a list, each line an item with its facts beneath it                                                  |
| provenance | Under each line, after its facts: Commit, Subject, Author, Committer, Trailers, Files, Reproduce; at the end the view's commands in a `Pre` |

- **The count line** reads `<n> event(s) in <m> commit(s), <first day> to <last day>: ` and the six kinds, each as its count and its key, zeros included: `1 task, 1 authorised, 4 status, 0 reaffirmed, 2 reviewed, 0 pin.` One day prints once; no line prints no day.
- **The cells of a line.** Event is the kinds joined by `, `, with ` (proposal)` after them when `Proposal`. Task is the task (R4). The last cell is the first of these the line holds: the status phrase (R3); the gate (R2) of a review; ``<url> `<old>` → `<new>` ``, or ``<url> new `<new>` `` for a first pin, hashes cut to seven; `the task file appears` for a task event.
- **The day fold (D1).** When the lines number more than fifty, the glance prints the day table and, in place of the line table, `**<n> lines fold into the days above.**` `Options.Unfold` lists them. Detail and provenance never fold. The run fold (R10) does not apply: no two lines agree in every cell.
- **A day at detail** opens `## <date> · <n> event(s) in <m> commit(s): ` and the day's kinds. A line is an item, `**<date>** · <by> · <event> · <task> · <last cell>`, and its facts are a nested list, each only when the data holds it, in this order: `Status after:` the phrase, with `, unchanged` when `Unchanged`; `Note:` the note of `Status`; `Effect:` the words below; ``<subject> after:`` the phrase, in a subtree's history; `Model:` as below; `Committer:` the email; `Subproject events:` ``<n> event(s) in <m> commit(s) of `<url>` `` with one nested item per line, `<date> · <by> · <event> · <task> · <last cell> · <model>`.
- **Effect** words a key: `authorised-commit`, `an authority commits the task file on the trunk, so the task is authorised`; `authorised-merge`, `an authority merges the change, so the task is authorised`; `authorised-trailer`, `an authority's trailer authorises the task`; `proposed`, `no authority accepts the change, so the task stands proposed`; `handoff`, `the contributor hands the work to the reviewer`; `accepts`, `the reviewer accepts the work at the gate`; `stands`, `none; the authorisation stands as the review`; `none`, `none`. Another key prints as it is.
- **Model** reads, by `Reading`: `agrees`, ``<model>; the <gate> junction states <stated>``, both models in code spans; `differs`, the same with `, which differs`; `missing`, ``no trailer; the <gate> junction states <stated>``; `exempt`, `none recorded; exempt`; with no reading and a trailer, the model alone.
- **Provenance facts.** Commit is the full hash (R6). Author and Committer read `Name <email>, <time>` as Git writes them. Trailers and Files are code spans joined by `, `, a file with its change in brackets. Reproduce holds the line's commands in a `Pre`.
- **Title, parameters, empty form.** The title carries the subject: ``# History: `e9c6` Abstract views``; the whole project prints `# History`. A range shows in the frame's ref (design e3ed) and in the command as `--ref <from>..<name>`. With no line, `**No event in view.**` follows the count line.

Related views: gates, task, queue, audit, tableau.

### The audit

```go
// Audit is the audit view.
type Audit struct {
	Head
	Findings    []Finding  `json:"findings"` // errors, warnings, information; then rule, gate, display order
	Errors      int        `json:"errors"`   // counts of findings, one per task a rule hits
	Warnings    int        `json:"warnings"`
	Information int        `json:"information"`
	Most        *Resolving `json:"most"`     // the person with the most to resolve; nil when none
}

type Resolving struct {
	Email string `json:"email"`
	Count int    `json:"count"`
}

// Finding is the tasks one rule hits at one gate for one reason.
type Finding struct {
	Rule     string    `json:"rule"`     // the code of corpus/RULES.md; empty for a proposed task and a stale status
	Severity string    `json:"severity"` // error, warning, information
	Kind     string    `json:"kind"`     // the rule in a few words: worded text (R17)
	Tasks    []TaskRef `json:"tasks"`
	Gate     string    `json:"gate"`
	Files    []string  `json:"files"`
	Message  string    `json:"message"`  // worded text
	Action   string    `json:"action"`   // worded text
	Resolver string    `json:"resolver"`

	Sentence string    `json:"sentence"` // provenance from here: the rule's sentence in the method
	Source   Reference `json:"source"`   // where the sentence stands
	Facts    []Fact    `json:"facts"`    // worded pairs: the junction, the reading
	Commits  []Commit  `json:"commits"`  // the commits involved, oldest first
	Commands []Command `json:"commands"` // what shows the finding, then what resolves it
}
```

| Level      | Blocks, in order                                                                                                                             |
|------------|----------------------------------------------------------------------------------------------------------------------------------------------|
| glance     | The count line, in bold; the table Severity, Rule, Kind, Findings, Tasks, Resolver, one row per severity and rule; the line `**Most to resolve:** <email>, <n> of <total>.` |
| detail     | The count line with `in <n> row(s)`; the table Rule, Severity, Task, Gate, File, Message, Action, Resolver, one row per `Finding`; the Most to resolve line |
| provenance | After the detail: one `##` section per `Finding`, with its rule, its facts, its commits and its commands                                       |

- **The count line** reads `**<n> error(s), <n> warning(s), <n> item(s) of information**: <total> finding(s).`, every severity named, zeros included.
- **The glance table** merges the findings of one severity and rule: Findings is the sum of their task counts; Tasks lists the tasks in the data's order, each once, as ids, or as one task by R4; Kind is the first finding's; Resolver lists the resolvers in the data's order, each once, joined by `, `.
- **The detail table.** Task is one task by R4 or several ids. Gate is the gate (R2). File is the files as code spans joined by `, `. Message and Action are worded text.
- **A provenance section** opens ``## <rule>, <severity>: <tasks> at <gate>`` and holds: `**Rule.** ` the sentence in quotation marks and its source as a link (R13); one paragraph per fact, `**<name>.** <value>`; the table Commit, Date, Author, Committer, Subject, Trailers, with Committer empty where it equals the author; the commands in a `Pre`, each under its comment.
- **Parameters and the empty form.** `stale <n> days` stands in the frame always, since the age decides what the view holds. `person` selects the findings one person resolves; tablo filters, and the counts are of what arrives. With no finding the count line reads zeros and `**No finding.**` replaces the table; the Most to resolve line does not print.

Related views: history, task, queue, tableau.

### What the design keeps from the prototype

From `prototype/9167` it keeps the merge of one commit's events on a task into one line, the count line, errors first, and commands in a fenced block. It drops the single Detail column that mixed gate, state and note, the `Range` column of the audit (VIEWS.md gives the audit a ref and no range), the labels `-range` and `-stale` that only named what the data covers (the frame reads them from `params`), and the stand-in rule names.

## Implementation notes

The task follows `e3ed` for the shared packages and `a3cc` for `count.go` and `view.KindCount`; if it lands before `a3cc`, it adds those two and `a3cc` finds them there. It adds `history.go`, `audit.go`, the two view files and its test data. `prototype/9167/` stays until the unit gate passes, then goes. No dependency.

Findings for the texts, not edited here. "A commit at a junction" (audit H3 and H6) has no definition in the method; the renderer shows the junction tablo names in `stated_gate` and in a finding's `gate`, so the gap stays with tablo's Audit (`dada`). The audit mockup's Silent section needs, per rule, the reason the rule reports nothing, which no part of VIEWS.md's audit data names (U3).

## Decisions at review

1. **The day fold.** The history's glance shows the day table from three days and folds its lines above fifty. The alternatives: no fold, so that `history` over a year prints every line; or a fold in tablo's data, which fixes one threshold for every front end.
2. **Fixed words for an effect and a model reading,** from a key tablo sets. The alternative has tablo write each `Effect:` and `Model:` sentence, as the mockup's prose suggests; the front ends then cannot word them apart, and the sentences grow project by project.
3. **One provenance section per finding,** with fixed commit columns and worded facts. The alternative keeps the mockup's section per rule and its rule-specific column, which needs a layout per rule in every front end.
4. **No Silent section** in the audit (U3). The alternative has tablo's Audit emit, per rule that reports nothing, a worded reason, and the renderer list them at glance.
5. **Every id in a cell that lists tasks** (U1), under e3ed's decision 8. The alternative abbreviates a list to its ends and a count, `` `99f0` … `a8b4`, twenty ``, which reads well only when the ids are a known run.
